# ADR-0022: Мгновенная настройка и явные режимы взаимодействия

**Статус:** принято; требуется реализация
**Дата:** 2026-10-13

## Контекст

Пользователь подтвердил живое редактирование оформления, автоматизаций и triggers. Готовое действие или виджет из библиотеки должно ускорять настройку, сохраняя возможность менять состав, расположение, переменные и взаимодействие каждого элемента. Ручной и адаптивный выбор панели должны быть взаимоисключающими режимами, включаемыми заданной кнопкой. Ошибка automation должна быть видна без автоматического повтора.

Текущий desktop Фазы 6 требует ручного Apply и сохраняет оформление как макет. Его приёмка остаётся исторически достоверной, но не доказывает выполнение этих новых требований. Hardware renderer, расширенная модель жестов и adaptive scenes ещё требуют своих срезов.

## Решение

- Валидные завершённые изменения автоматически проходят существующий durable draft → validate/prepare → atomic commit. Apply остаётся внутренней операцией host; обязательная кнопка подтверждения исчезает из обычного сценария. Незавершённая форма не заменяет последнюю рабочую конфигурацию.
- Перемещение визуального объекта показывает свежую позицию сразу через bounded preview/output path. Пиксельные обновления объединяются по принципу latest-wins; жест образует одну undo-операцию. Сохранение и compilation не обязаны выполняться на каждом кадре. Unchanged plugin instances, subscriptions и ресурсы не перезапускаются при изменении оформления.
- Обновление конфигурации само по себе не выполняет её action. Старый удержанный ввод не становится новым press; replay state при подписке не считается новым событием. Уже начатые runs/held outputs следуют существующим epoch/cleanup rules, а не переадресуются новым bindings.
- В scope устройства или явно связанной группы активен ровно один режим выбора панели: manual либо adaptive. В manual foreground events не переключают панель. В adaptive используется правило для актуального активного окна, иначе стандартная панель; при включении режима оценивается и уже активное окно. Runtime switching не переписывает workspace.
- Кнопка-модификатор имеет явные solo/chord bindings. Solo выполняется на отпускании после нажатия без участия в сочетании; chord подавляет solo внутри DeckWeave. Cancel/disconnect/rearm не выполняют solo. Это модель жеста, а не обещание перехвата системного ввода; OS suppression требует отдельного provider capability.
- Высокоуровневое действие открытия приложения выбирает существующее окно, если оно найдено, иначе запускает программу. Exact launch и activate остаются самостоятельными низкоуровневыми действиями. Отказ в focus не является основанием запустить второй экземпляр.
- Ошибка зависимого шага останавливает эту цепочку и показывает краткое уведомление; details доступны в diagnostics. Автоматического повтора business action нет. Recovery транспортного запроса с тем же command ID не является повторным исполнением действия.

## Последствия и проверки

Пользователь получает знакомый сценарий «перетащить, настроить, использовать» и свободный визуальный редактор для кнопок и панелей. Возможности отображения и ввода определяются независимо: отсутствие touch не мешает картинке, наличие координат не доказывает hold/drag/pressure.

Существующие immutable revisions, fences, grants и cleanup сохраняются. До включения live apply проверить: invalid intermediate input, latest-wins при медленном prepare, ошибка сохранения, undo, disconnect, редактирование во время hold/run, отсутствие повторного action при подключении state и отсутствие рестартов providers при визуальном перемещении. Hardware preview не получает гарантии физического отображения по одному факту принятия команды.

Production coordinator сохраняет execution epoch, процессы, subscriptions, pending runs и deadlines, если новая revision имеет тот же executable graph, compiler identity и runtime requirements, а grants, registry bindings и health остаются действительными. Planning digest сравнивать для этого недостаточно: он включает меняющиеся fences. Повторная проверка выполняется перед durable commit и при публикации его результата; ошибка остаётся явной. Для такого обновления не закрывается execution barrier. Изменённая automation, настройки instance, разрешения либо неисправный runtime проходят обычный cutover с cleanup; перенос runs в изменённый граф не поддерживается. Recovery после перезапуска host всегда создаёт новую execution epoch. Instances с credentials пока проходят обычный cutover: один CredentialRef не доказывает неизменность секрета после ротации; для их повторного использования нужен versioned credential evidence.
