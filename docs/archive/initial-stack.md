# Я бы создавал новое ядро на Rust, а OpenDeck использовал как источник готовых решений

С учётом твоей новой концепции я больше не рекомендую начинать с форка OpenDeck.

Ты хочешь создать не альтернативу Stream Deck, а универсальную платформу управления, в которой клавиатуры, мыши, сенсорные панели, педали, регуляторы, рули и другие устройства могут совместно управлять приложениями и друг другом.

Это принципиально другой класс программного обеспечения.

Мой выбор: самостоятельный проект на Rust с новой архитектурой, но с повторным использованием существующих библиотек, протоколов и адаптеров плагинов. Не переписывать всё с нуля и не наследовать архитектурные ограничения OpenDeck.

## 1. Почему не стоит строить всё на форке OpenDeck

У [OpenDeck](https://github.com/nekename/OpenDeck) основная единица управления — кнопка или регулятор Stream Deck, связанный с экземпляром действия плагина. Контекст включает устройство, профиль, тип контроллера и позицию элемента. Это видно в [описании архитектуры проекта](https://github.com/nekename/OpenDeck/blob/main/AGENTS.md).&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub

+1



Для обычной панели с LCD-кнопками такое представление подходит. Но тебе нужна более универсальная модель:

- Аналоговая клавиша сообщает не только нажатие, но и величину хода.
- Поворот регулятора может менять назначение других органов управления.
- Кнопка одной клавиатуры активирует временный режим сразу на нескольких устройствах.
- Сенсорная поверхность может распознавать координаты и жесты, а не только четыре фиксированные области.
- Несколько устройств образуют одну общую рабочую поверхность, но остаются независимыми физическими устройствами.
- Один сценарий может одновременно изменять программное состояние, изображения LCD-клавиш, подсветку и параметры других контроллеров.

Если последовательно добавлять эти возможности в архитектуру, ориентированную на Stream Deck, придётся переделывать модель устройства, систему профилей, обработку событий, плагины и интерфейс.

Это не означает, что OpenDeck плохо написан. Просто его основная задача значительно уже твоей.

Как я бы распределил существующие проекты

| OpenDeck           | Источник реализации хоста Elgato/OpenAction и архитектурных решений                                 |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| mirajazz           | Готовая Rust-библиотека для устройств Mirabox/Ajazz                                                 |
| SDK Mirabox        | Источник аппаратных команд и реализации особенностей N4 Pro                                         |
| Wooting Analog SDK | Пример подключения клавиатур с аналоговыми значениями нажатия и расширения через драйверные плагины |
| Новое Rust-ядро    | Универсальная модель устройств, общие состояния, логика взаимодействия и API                        |

Такое решение позволит использовать накопленную работу сообщества, не привязывая будущие возможности программы к ограничениям одного проекта.

## 2. Ближайшие по концепции проекты — не OpenDeck

Нашёл три проекта, архитектуру которых стоит изучить даже внимательнее, чем OpenDeck.

[InputPlumber](https://github.com/ShadowBlip/InputPlumber)

Написанная на Rust система для Linux. Объединяет несколько физических устройств в одно логическое, маршрутизирует события и создаёт виртуальные клавиатуры, мыши и геймпады.

Это почти готовый образец того, как реализовывать совместную работу нескольких устройств. Но проект ориентирован на Linux и распространяется под GPLv3+.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



[Kanata](https://github.com/jtroo/kanata)

Кроссплатформенный переназначатель клавиатуры на Rust. Поддерживает слои, макросы, различные действия для короткого и долгого нажатия.

Отсюда стоит перенять не весь механизм клавиатуры, а модель временных слоёв управления и композиции сочетаний.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



[Wooting Analog SDK](https://github.com/WootingKb/wooting-analog-sdk)

Кроссплатформенный SDK на Rust для аналоговых клавиатур. У него уже есть собственная система плагинов устройств, включая реализации через Rust и C ABI.

Особенно полезен для изучения нормализации аналоговых значений, обнаружения устройств и подключения драйверов производителей.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

+1



Здесь есть важное терминологическое уточнение: у большинства магнитных клавиатур с датчиками Холла измеряется ход клавиши, а не непосредственно сила нажатия. Поэтому в ядре нужно хранить тип физической величины: ход, сила, угол, скорость вращения и т. д., а не считать любую аналоговую величину давлением.

Для будущей платформы я бы объединил три идеи:

InputPlumber — несколько устройств образуют одну систему.

Kanata — назначение органов управления зависит от активного слоя, удерживаемых клавиш и контекста.

OpenAction — действия в приложениях можно добавлять через существующий открытый интерфейс плагинов, совместимый с большой частью экосистемы Stream Deck.&#x20;

## 3. Основа архитектуры — возможности устройства, а не его тип

Это самое важное проектное решение. Я бы вообще отказался от предположения, что программа знает такие классы, как «Stream Deck», «клавиатура» или «руль».

Вместо этого каждое устройство сообщает, какими элементами оно располагает.

| Универсальная возможность | Пример физического устройства                   |
| ------------------------- | ----------------------------------------------- |
| `Button`                  | Клавиша, педаль, переключатель                  |
| `AnalogInput`             | Магнитная клавиша, педаль газа, датчик давления |
| `Encoder`                 | Бесконечный регулятор, колёсико                 |
| `Axis`                    | Джойстик, руль, потенциометр                    |
| `TouchSurface`            | Сенсорная полоса, тачпад, экран                 |
| `Display`                 | LCD-клавиша, сенсорный экран, внешний монитор   |
| `Light`                   | RGB-клавиша, светодиодное кольцо                |
| `HapticOutput`            | Вибрация, тактильный отклик                     |
| `MotionInput`             | Акселерометр, гироскоп                          |
| `ForceFeedback`           | Руль с обратной силовой связью                  |

Это не закрытый перечень: драйвер может объявлять новые возможности, если пользовательский интерфейс пока не умеет их специализированно отображать.

При этом нужно различать физические события и логические действия.

Например, поворот регулятора вправо — физическое событие. Увеличение громкости — действие. Но в другом режиме тот же поворот может увеличивать масштаб документа, изменять яркость SprutHub или переключать задачу SingularityApp.

Одно устройство при этом может быть одновременно источником событий и средством обратной связи.

Логическая схема желаемой системы; все действия являются примерами будущей реализации.

И это лишь один пример. В дальнейшем аналоговая клавиша может постепенно изменять параметр пропорционально глубине нажатия, а педаль — временно активировать инструменты сразу на нескольких устройствах.

Вместо независимых профилей каждого устройства нужны общие рабочие пространства, внутри которых могут существовать временные слои, режимы и локальные исключения.

Это гораздо масштабируемее традиционной схемы «одна кнопка — одно действие».

## 4. Архитектура нового ядра на Rust

Я бы выделил семь независимых подсистем. Это позволит заменять реализацию драйверов, интерфейса и плагинов без переписывания всего приложения.

Device Providers

Условия · слои · маршрутизация · сценарии · последовательности

Windows, API, скрипты, приложения

LCD, RGB, вибрация, обратная связь

Plugin Compatibility

OpenAction, Elgato, адаптеры

Local API / MCP

Desktop UI — Tauri 2 + Svelte

Редактор устройств, схем управления, плагинов и автоматизации

### Система плагинов

Здесь я бы не повторял разделение OpenDeck на плагин устройства и плагин действия как две практически отдельные экосистемы. Нужен единый формат пакета расширения, который может предоставлять одну или несколько возможностей.

| Возможность плагина | Назначение                                                                     |
| ------------------- | ------------------------------------------------------------------------------ |
| `DeviceProvider`    | Обнаружение устройств, получение событий, управление физическими возможностями |
| `ActionProvider`    | Действия: отправить команду, открыть приложение, выполнить скрипт              |
| `StateProvider`     | Данные: текущая задача, состояние VPN, активное окно                           |
| `RendererProvider`  | Специализированная визуализация для LCD, RGB и экранов                         |
| `ProtocolBridge`    | Подключение плагинов других экосистем, прежде всего OpenAction/Elgato          |

Например, плагин SprutHub может предоставлять действия включения света, получать фактическое состояние устройств и создавать собственные элементы интерфейса. Плагин N4 Pro может предоставлять органы управления, экраны и RGB-подсветку. Оба используют один механизм установки, жизненного цикла, разрешений и диагностики.

Технически: плагины я бы запускал в отдельных процессах и связывал с Rust-ядром через версионированный протокол IPC. Это позволит писать их не только на Rust, но и на Python, JavaScript и других языках. Нативные плагины не следует считать изолированными только потому, что они работают в отдельном процессе; для них нужны разграничение разрешений и модель доверия. В дальнейшем можно добавить WASM-плагины для более ограниченного выполнения.

### Чтобы не потерять существующие плагины

Нужно с самого начала заложить отдельный OpenAction/Elgato Compatibility Host, который реализует опубликованный WebSocket-протокол и загружает существующие манифесты плагинов.

OpenAction уже позиционируется как независимый от платформы и конкретного устройства API, обратно совместимый с Stream Deck SDK. Его документация и Rust-библиотека открыты.&#x20;

Но стандартный интерфейс Elgato рассчитан прежде всего на кнопки, регуляторы и соответствующие экраны. Для аналоговых клавиатур, сенсорных поверхностей и нескольких связанных устройств потребуется собственное расширение протокола. Обратная совместимость должна сохраняться внутри адаптера, а не ограничивать универсальное ядро.

Важно по лицензиям: новый проект я бы выпускал под Apache-2.0/MIT. Код OpenDeck (GPL) не переносил бы в ядро напрямую. Совместимость реализовал бы на основе опубликованных протоколов; существующие MIT/MPL-библиотеки использовал бы с соблюдением их условий. Так остаётся больше свободы для дальнейшего развития и распространения проекта.

## 5. Как сделать добавление нового устройства действительно простым

Я вижу здесь ключевую функцию будущей программы: Device Studio.

Не должно быть необходимости изучать USB-протокол и писать Rust-драйвер для каждой новой клавиатуры или обычного HID-контроллера.

Предлагаемый процесс подключения

1. Обнаружение

   Пользователь подключает устройство. Программа показывает его идентификаторы, интерфейсы и доступные HID-функции.
2. Определение органов управления

   Если устройство стандартное, кнопки, оси и регуляторы определяются автоматически. Для нестандартного — пользователь нажимает на элемент и видит полученные события.
3. Назначение возможностей

   Пользователь указывает, что обнаруженный сигнал соответствует кнопке, оси, регулятору, аналоговой клавише или сенсорной области. Для осей можно задать диапазоны, мёртвые зоны и кривые отклика.
4. Генерация адаптера

   Программа сохраняет декларативное описание устройства. Codex при необходимости дописывает специальный Rust-драйвер, пользуясь записанными примерами пакетов и проверочными тестами.
5. Подключение к системе

   Устройство появляется в общем редакторе и может участвовать в автоматизациях совместно с остальным оборудованием.

Для стандартного HID этого в значительной части можно достичь без написания кода. Для устройств с закрытым протоколом, нестандартными отчётами или фирменным ПО потребуется специализированный адаптер. Автоматическое распознавание абсолютно любого оборудования обещать нельзя.

В Device Studio также нужен виртуальный эмулятор: чтобы можно было тестировать новый драйвер без физического устройства. Для открытого проекта это особенно важно — участники смогут разрабатывать и проверять расширения, не покупая всё существующее оборудование.

## 6. Кроссплатформенность: основная сложность будет не в Rust

Для будущей системы я бы сразу закладывал Windows, Linux и macOS, но разрабатывал и испытывал полноценную реализацию сначала на Windows.

Главная причина — различия в системах обработки ввода.

| Возможность                          | Windows                                             | Linux                       | macOS                                   |
| ------------------------------------ | --------------------------------------------------- | --------------------------- | --------------------------------------- |
| Чтение специальных USB HID-устройств | Есть системные API                                  | `hidraw`, evdev             | IOKit / HID                             |
| Наблюдение за клавиатурой            | Raw Input и системные события                       | evdev, libinput             | Event Taps и соответствующие разрешения |
| Блокировка/подмена обычных нажатий   | Дополнительные механизмы, ограничения               | evdev/uinput, права доступа | Accessibility и системные ограничения   |
| Виртуальная клавиатура и мышь        | Windows API, для отдельных вариантов нужны драйверы | uinput и другие механизмы   | Системные API и разрешения              |
| Плагины Elgato                       | Реализация хоста                                    | Реализация хоста            | Реализация хоста                        |

Очень важное ограничение: Windows открывает стандартные HID-коллекции клавиатур и мышей для системного использования в эксклюзивном режиме. Поэтому нельзя рассчитывать, что произвольную обычную клавиатуру удастся открыть через `hidapi` и полностью перехватить её работу. Для наблюдения за устройствами есть Raw Input, а полноценное избирательное переназначение требует других решений.&#x20;

| 0. Спецификация  | Описания устройства, событий, состояний, действий и протокола плагинов | Типы данных проверяются на виртуальных устройствах                          |
| 1. Rust Core     | Реестр устройств, общие события, состояния, слои и маршрутизация       | Событие одного устройства меняет поведение другого                          |
| 2. Драйверы      | N4 Pro, клавиатура-наблюдатель, виртуальное устройство                 | Одновременно работают три разных источника                                  |
| 3. Автоматизация | Сценарии, условия, временные слои, обратная связь                      | Удержание клавиши меняет назначение регулятора и оформление LCD             |
| 4. API и MCP     | Чтение и изменение конфигурации, запуск тестов, диагностика            | Codex создаёт сценарий без ручного редактирования файлов                    |

Ключевое условие первой рабочей версии: не нужно ждать завершения всех этих этапов, чтобы ежедневно использовать N4 Pro. После третьего этапа уже должен получиться полезный локальный инструмент.

## 10. Мой окончательный совет

Я бы начал DeckWeave как независимую Rust-платформу со следующими приоритетами:

Первый принцип — универсальные устройства. Любые физические органы управления описываются через возможности, а не через жёсткие типы оборудования.

Второй — общая система событий и состояний. Устройства могут влиять друг на друга, использовать общие слои и контексты, а не существовать как независимые панели.

Третий — совместимость с существующей экосистемой. OpenAction/Elgato должен быть одним из первых адаптеров, чтобы проект сразу получил доступ к готовым плагинам. Собственный API дополняет эту экосистему, а не отказывается от неё.

Четвёртый — API-first. Любое действие, которое пользователь выполняет в интерфейсе, должно быть доступно через локальный API. Тогда Codex сможет создавать устройства, редактировать сценарии, тестировать их и проверять результат.

Пятый — Windows-first, cross-platform by design. Rust-ядро остаётся независимым от операционной системы, а платформенные особенности изолируются в адаптерах.

Самый первый практический эксперимент я бы сделал таким:

> Подключены N4 Pro и обычная клавиатура. При удержании выбранной клавиши на клавиатуре четыре регулятора N4 Pro меняют функции. На дисплеях сразу появляются новые значения и назначения. После отпускания всё возвращается обратно. Конфигурация меняется через локальный API без перезапуска программы.

Если этот пример удастся реализовать архитектурно чисто, не вшивая знания о конкретных устройствах в ядро, значит фундамент выбран правильно.

Есть один вопрос, который стоит решить до написания архитектуры: ты хочешь, чтобы программа полноценно перехватывала и заменяла ввод обычных клавиатур и мышей, или достаточно получать события от них и запускать собственные автоматизации? Первый вариант существенно сложнее и определяет устройство всей платформенно-зависимой части.
