# Препроект DeckWeave

## Препроект

**Тип:** новый публичный open-source проект.

**Суть:** универсальное локальное приложение для композиции физических, виртуальных, программных и удалённых устройств. Всё, что создаёт данные, публикует типизированные output ports; всё, что реагирует, предоставляет command, value, frame, haptic или stream inputs. Простая связь выглядит как «орган управления → действие», а сложная раскрывается в условия, состояния, слои, последовательности, параллельные ветви и feedback.

**Пользователи:**

1. первоначально — один владелец DeckWeave и его устройств;
2. далее — другие владельцы панелей, клавиатур и геймпадов;
3. авторы device-, action-, state-, renderer- и media-плагинов;
4. участники публичного репозитория, в том числе без реального оборудования;
5. авторы автоматизаций и агенты вроде Codex, использующие стабильный локальный API.

**Ключевые сценарии:**

1. Пользователь видит все устройства на общем infinite canvas, выбирает элемент и назначает действие за 2–3 шага.
2. N4 Pro предоставляет десять кнопок, четыре энкодера с нажатием и подсветкой, общий сенсорный экран, вибрацию и другие подтверждённые hardware capabilities.
3. Один input меняет поведение нескольких устройств, активный слой или визуальную сцену.
4. Automation выполняет последовательные и параллельные шаги с выбранной политикой ошибок и показывает проблемный node.
5. Пользователь устанавливает plugin package, видит contributions и permissions, а runtime запускается только при использовании.
6. Существующий OpenAction/совместимый Elgato plugin работает через отдельный compatibility host без переписывания исходников.
7. Сценарий записывается и воспроизводится с fake clock для тестирования.
8. Codex читает, изменяет, валидирует и применяет конфигурацию через application API; MCP является необязательным adapter.
9. В будущем телефон или Steam Deck подключается как remote node с экраном, touch, камерой, микрофоном, динамиком и датчиками.
10. В будущем отдельный media runtime обрабатывает аудио/видео с низкой задержкой и предоставляет виртуальные endpoints.

**Технические упоминания:** Rust, Tokio, Tauri 2, Svelte/TypeScript, Rust/TypeScript/Python plugin SDK, Protocol Buffers для native control protocol, OpenAction/Elgato WebSocket compatibility, JSON Schema для settings, HID/Bluetooth, GStreamer/PipeWire/CLAP как media references.

**Неявные допущения:**

- DeckWeave полезен задолго до реализации всех задуманных классов устройств;
- host работает в пользовательской сессии, запускается автоматически и остаётся в tray после закрытия окна;
- один активный plugin package обычно соответствует одному изолированному процессу, а не процессу на каждую кнопку;
- plugin process isolation защищает от crash, но не является полной sandbox для злонамеренного кода;
- UI не находится в критическом пути device events;
- редкие и тяжёлые функции поставляются отдельно и не увеличивают baseline;
- firmware flashing не входит в DeckWeave;
- memory programming устройства допускается только через явно заявленную безопасную capability;
- совместимость означает проверяемый уровень для конкретной версии plugin, а не обещание «работает всё».

**Открытые вопросы, не блокирующие начало:**

- первый набор открытых OpenAction packages для compatibility matrix;
- формат подписи публичного каталога и release artifacts;
- конкретный Windows-механизм полного selective interception обычных клавиатур;
- первый media backend после стабилизации control plane;
- допустимые ограничения sandbox для custom web widgets на каждой ОС.

## Критический разбор требований

### Подтверждаем

- **Рабочее пространство выше отдельного устройства.** Это позволяет нескольким физическим и виртуальным узлам разделять состояния, слои и feedback.
- **Progressive disclosure вместо двух режимов UI.** Простая форма и drag-and-drop остаются основным путём, а graph и расширенные настройки раскрывают ту же конфигурацию.
- **Устройства и системные интеграции — плагины.** N4 Pro и Windows не становятся особыми случаями core.
- **API-first нужен с начала.** Иначе Codex, CLI и UI неизбежно получат разные возможности.
- **Процессная изоляция важнее абсолютного минимума RAM.** Lazy activation и один runtime на package дают разумный компромисс.
- **OpenAction/Elgato совместимость нужна рано.** Это снижает риск «мёртвого» проекта без экосистемы.
- **Control и media paths должны быть разделены.** Ни JSON, ни async automation engine не подходят для audio callback.
- **Полный canvas и touch coordinates являются базовой моделью surface.** Фиксированная сетка — только template и snap, а не аппаратное ограничение.

### Принятые изменения

- **Не отдельный daemon в первой версии:** один per-user desktop host владеет tray и runtime; закрытие окна скрывает UI, но не завершает host. Headless host остаётся будущим режимом того же application core.
- **Не автоматическое переписывание чужих плагинов:** неизменный package запускается compatibility host; нативная замена создаётся отдельно и мигрирует settings только по явному правилу.
- **Не единый ABI для всего:** общий manifest и capability vocabulary сочетаются с отдельными control, compatibility, widget, media и remote runtime classes.
- **Не event sourcing для пользовательской истории:** draft поддерживает undo/redo, применённые revisions и именованные snapshots; экспорт/импорт остаётся переносом и резервным копированием.
- **Не Python внутри core:** Python поддерживается как isolated plugin runtime для сложных условий и действий, но не участвует в real-time media thread.
- **Не «полная поддержка любой ОС» через core:** OS-dependent ввод, вывод, active-window и virtual devices предоставляются platform plugins/adapters.

## Подтверждённые архитектурные решения

1. Один per-user tray host; system service отсутствует в v1.
2. Installed и portable distributions используют одинаковое ядро и разные data roots/startup policy.
3. Полный keyboard interception предусмотрен контрактами, но не блокирует первую N4 Pro вертикаль.
4. OpenAction/Elgato bridge реализуется раньше Companion bridge.
5. Приложение/core лицензируются под `GPL-3.0-or-later`; protocol/SDK/examples — под `MIT OR Apache-2.0`.
6. Первый приоритет — N4 Pro; Bluetooth gamepad является ранней проверкой универсальности; гибкая клавиатура следует далее.
7. Windows 10/11 — первая платформа, Linux — вторая, macOS учитывается в design.
8. Undo/redo, revisions и snapshots дополняют выборочный экспорт/импорт.
9. Пользователь самостоятельно определяет доверие к plugin, но DeckWeave обязан показывать permissions, изолировать crash и диагностировать conflict.
10. Все действия UI должны иметь эквивалент в локальном API с optimistic concurrency, validation и dry-run.
